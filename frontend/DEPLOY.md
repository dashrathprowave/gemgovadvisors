# Deploying GeM Advisor

The site deploys itself: **push to `master` → GitHub Actions tests it → builds
the bundle → uploads it to the VPS → restarts → health-checks the live site.**

The copy-paste runbook (first-time setup, every command you will ever run) is
in **[CI-CD-STEPS.md](./CI-CD-STEPS.md)**. This file is the reference: how the
pipeline works, what the server needs, and how to fix what can break.

---

## 1. The pipeline

`.github/workflows/ci.yml` — triggers on every push to `master`, every version
tag (`v*`), and pull requests.

```
push
  │
  ▼
TEST jobs (ubuntu-latest, parallel)       ← pushes AND pull requests dono par
  test-frontend  (working-directory: frontend/)
    npm ci → npm run lint → npm test → npm run build → npm run smoke
    → node scripts/build-bundle.mjs       (sirf master push par — deploy.tar.gz)
  test-backend  (working-directory: backend/)
    compileall syntax check → pip install (CPU torch + requirements)
    → python -c "from main import app"   (router assembly check, no model download)
  │
  ├─ any step fails → nothing deploys, run goes red, you get an email
  │
  ▼
DEPLOY job (pushes to master/tags only — PRs never deploy)
  git pull on the VPS (repo root has frontend/ + backend/)
  → frontend/: npm ci → npm run build → pm2 restart frontend
  → backend/:  venv refresh → pm2 restart chatbot-backend
  → health check: GET 127.0.0.1:8000/health → must answer 200 (10 min tak retry —
    pehli boot par ML models download hote hain)
```

### Secrets (GitHub → Settings → Secrets and variables → Actions)

| Secret | Value |
| --- | --- |
| `VPS_HOST` | the server IP |
| `VPS_USER` | SSH user (`test_gem1` in the testing phase) |
| `VPS_PORT` | `22` |
| `VPS_PATH` | the site directory (`/var/www/<id>/public_html`) |
| `SITE_URL` | `https://test.gemgovadvisors.com` now — production switch is a checklist in CI-CD-STEPS.md Step 11 |
| `VPS_SSH_KEY` | the deploy **private key** — lives only in GitHub, never in the repo |

### Why a bundle, not the whole project

The server has no Next CLI — a full project would need `npm install` and
`next build` on the VPS, which is slow and runs out of memory on small
instances. `deploy.tar.gz` is already built and carries only what runs:

| | |
| --- | --- |
| `server.js` | the app (Next standalone output) |
| `start.js` | the panel's startup file — loads `.env.local`, then hands over to `server.js` |
| `node_modules/` | trimmed; includes `mysql2` and `nodemailer` |
| `.next/`, `public/` | the built site, styles, images |
| `db/`, `scripts/` | schema + `db-setup`, `db-check`, `mail-test`, `db-export` |

`.env.local` and `data/` are deliberately **not** included — secrets and stored
enquiries belong on the server only.

Manual fallback (CI unavailable): `npm run bundle` → upload `deploy.tar.gz` →
on the server `rm -rf .next && tar -xzf deploy.tar.gz` → **restart from the
panel**.

## 2. Why `rm -rf .next` before extracting

`tar` overwrites but never deletes. Extracting a new build on top of an old one
leaves `.next/server` and `.next/static` holding files from two different
builds. The page is then generated by one build while asking for asset
filenames from the other — Apache misses them, passes the request to Node, and
you get a 500 on a stylesheet with everything else working. The pipeline always
deletes first (and keeps the previous build as `.next-prev` for rollback).

Do not upload the folder file-by-file either: `.next/static` holds thousands of
tiny files and FTP/file managers routinely drop a few — one missing CSS chunk
kills all styling with nothing in the logs.

## 3. Server setup (one-time, per site)

### `.env.local`

Created **on the server**, next to `start.js` — never uploaded:

```bash
# Enhance runs MySQL on a unix socket, not a TCP port
MYSQL_SOCKET=/run/mysqld/mysqld.sock
MYSQL_USER=<database user from Enhance>
MYSQL_PASSWORD=<its password>
MYSQL_DATABASE=<database name from Enhance>

SMTP_HOST=smtp.hostinger.com
SMTP_PORT=465
SMTP_USER=gem@gemgovadvisors.com
SMTP_PASSWORD=<the mailbox password>

HOSTNAME=0.0.0.0
```

- **`HOSTNAME=0.0.0.0`** — Enhance proxies to the app; bound only to
  `localhost` it gives a 502.
- **Never set `PORT`** — Enhance assigns it.
- Port 465 blocked? Use `SMTP_PORT=587`.
- Socket path unknown? `ls -la /run/mysqld`. Host exposes MySQL over TCP
  instead? Drop `MYSQL_SOCKET`, use `MYSQL_HOST=127.0.0.1` + `MYSQL_PORT`.

### Database

```bash
node scripts/db-setup.mjs    # creates tables — safe to re-run
node scripts/db-check.mjs    # row counts + "Email alerts: SMTP (...)" must not say OFF
node scripts/mail-test.mjs   # sends one real test email
```

### Start the app — Enhance **Deploy Node.js** tool

| Field | Value |
| --- | --- |
| Application root | the site directory |
| Startup file | **`start.js`** — not `server.js` |
| Node version | 20+ |

`start.js` reads `.env.local` itself before handing over to `server.js`, and
prints whether that worked:

```
[start] env vars loaded: 9 | database: configured | email: configured
```

`MISSING` → `.env.local` is not next to `start.js`. Without those vars the app
runs, forms "succeed", and enquiries silently fall through to `data/` with no
error anywhere.

## 4. Restart semantics (what actually happens on deploy)

The pipeline kills the old process after extracting:

```
pkill -f '[n]ode.*start.js' | '[n]pm start' | '[n]ode.*server.js'
```

- If Enhance's supervisor restarts the app on its own → fully automatic.
- If it does not, the health check fails (site answers nothing) and the job
  goes red — that is your signal: **press Restart in the panel**, then re-run
  the failed job.

Either way the pipeline never reports success while the site is down.

## 5. Rollback

**Preferred** (code-level):

```bash
git log --oneline          # find the bad commit
git revert <hash>
git push                   # pipeline deploys the previous state
```

**Files only** (server, then restart from the panel):

```bash
cd /var/www/<id>/public_html
rm -rf .next && mv .next-prev .next
```

## 6. Email deliverability

Mail goes from the site's own mailbox — without these records it lands in spam.
Hostinger usually adds them for its mailboxes; confirm they exist:

- **SPF** — `v=spf1 include:_spf.mail.hostinger.com ~all`
- **DKIM** — the record Hostinger generates for the domain
- **DMARC** — `v=DMARC1; p=none; rua=mailto:gem@gemgovadvisors.com`

## 8. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Deploy job: `Permission denied (publickey)` | The public key is missing from `test_gem1`'s `~/.ssh/authorized_keys` |
| Deploy job: `Host key verification failed` | `ssh-keyscan` step could not reach `VPS_HOST:VPS_PORT` — check the secrets |
| Health check red after setup | App not running, `HOSTNAME` ≠ `0.0.0.0`, or SSL off for the domain — check the `[start]` log line |
| Lint / test / smoke step red | Run the same command locally (`npm test`, `npm run smoke`) — the failure reproduces |
| Backend job red (`compileall` / import) | Run it locally in `backend/` with the venv python — same failure reproduces |
| Backend health check red (deploy) | `pm2 logs chatbot-backend --lines 50` on the VPS. First-ever deploy downloads ~3 GB of models — needs 10+ min and enough disk/RAM |
| Backend 502 from the site widget | Backend process down — `pm2 list` / `pm2 restart chatbot-backend`; site itself keeps working |
| Site loads, layout broken / mobile-looking | Mixed builds. Roll back: `rm -rf .next && mv .next-prev .next`, restart, re-run |
| 502 / bad gateway | App not running, or `HOSTNAME` is not `0.0.0.0` |
| Form succeeds but no database row | `MYSQL_*` wrong — `node scripts/db-check.mjs`; the enquiry is safe in `data/registrations.json` |
| No alert emails | `SMTP_*` wrong, or port 465 blocked — try 587 |
| `next: not found` on the server | You ran a build command there — builds happen on your machine/CI only |
| Forms fall through, `[start]` says MISSING | `.env.local` not next to `start.js` |
| Deploy job shows *skipped* | Push was a PR (by design) or not on `master`/`v*` |

## 9. Chatbot backend on the VPS

The backend (FastAPI, `backend/`) deploys in the same `deploy` job as the
frontend — one `git pull` brings both. On the server it runs as a pm2 process:

```bash
pm2 list                        # expect: frontend + chatbot-backend, both "online"
pm2 logs chatbot-backend --lines 50
pm2 restart chatbot-backend     # after changing backend/.env
```

### `backend/.env` (on the server, never in git)

Created once from `backend/.env.example` (see `backend/deploy/setup-vm.sh`).
Must set: `DATABASE_URL` (Postgres + pgvector), `LLM_API_KEY` (Groq),
`ADMIN_USERNAME` + `ADMIN_TOKEN`, `REDIS_URL`, MySQL `probid` credentials.
The file is gitignored — the deploy never overwrites it.

### How the site reaches the backend

The Next.js routes (`/api/chat`, `/api/user/register`, `/api/admin/*`) proxy
to `CHATBOT_API_URL`, default `http://127.0.0.1:8000`. Same-machine default
works with zero config; only set it if the backend lives on another host.

### First deploy takes a while

The first backend boot downloads ~3 GB of embedding models into the HF cache
and loads them into RAM. The CI health check retries up to 10 minutes for
exactly this reason. Later deploys reuse the cache and restart in ~1 minute.

### Postgres/pgvector + MySQL on the VPS

The backend needs both databases reachable with the credentials in
`backend/.env` (same as local: `ragdb` + `probid`). They are **not** created
by CI — set them up once per server (`backend/deploy/setup-vm.sh` has the
commands, including `schema.sql` + `users-table.sql`).
